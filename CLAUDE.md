# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

- `backend/` — **Hono + TypeScript on Vercel Functions, Drizzle ORM.** Ported from NestJS + TypeORM (see git history if you need the old shape) specifically because Nest's DI graph + TypeORM connection setup cost ~2s on every cold start, and Vercel's zero-config NestJS builder had already forced a Docker container deploy after silently mis-bundling `main.ts`. Compiled to CommonJS (`"module": "commonjs"`, plain relative imports, no `.js` extension), package manager **pnpm**.
  - **Entry point is `src/index.ts`**, not `main.ts` — Vercel's Hono zero-config detection only recognizes `app.ts`/`index.ts`/`server.ts` (or the `src/` equivalents) with `export default app`. `vercel.json`'s `backend` service also needs an **explicit `entrypoint: "src/index.ts"`** even though Hono is zero-config — under Vercel's multi-service `services` model every service needs an explicit entrypoint regardless of framework auto-detection (confirmed by deploying an isolated throwaway Hono service before porting anything real). `src/index.ts` only ever does `export default app`; local dev instead runs `src/dev-server.ts`, which wraps the same `app` with `@hono/node-server`'s `serve()` — Vercel Functions must never call `serve()`/bind a port themselves. API routes are prefixed `/api` (mounted via `app.route('/api/...', ...)` in `index.ts`), except `/` and `/health` which stay unprefixed ops endpoints.
  - **DB is Supabase Postgres** via `drizzle-orm/postgres-js`, connecting through the transaction pooler (port 6543) with **`prepare: false`** — required for pgbouncer transaction-pool mode, and a new constraint that didn't exist under `pg`/TypeORM. SSL: `postgres(DATABASE_URL, { ssl: { ca: DATABASE_CA_CERT } })` — the `postgres-js` driver takes the URL string and `ssl.ca` together without issue (verified directly; this was the single biggest risk in the port given `pg`'s equivalent silently broke on `sslmode=require` in the URL — see the still-relevant warning below). `src/db/client.ts` creates the `postgres()` client once at module scope so warm Vercel invocations reuse the connection. `src/db/schema.ts` is hand-tidied from a one-time `drizzle-kit pull` against the live DB — column names map snake_case↔camelCase same as before, `proposals.status`/`discount_type`/`proposal_items.price_type` are `varchar` with `.$type<...>()` (never became real Postgres enums), and every `updated_at` column carries an explicit `.$onUpdate(() => sql`now()`)` since TypeORM used to do that in JS with no DB trigger backing it — easy to lose in a schema edit, don't. `drizzle-kit` now owns all future schema changes (`pnpm run db:generate` / `db:migrate` against `drizzle.config.ts`); the old TypeORM migrations in `src/database/migrations/` are kept only as historical record (excluded from `tsconfig.json`, `typeorm` is no longer a dependency) — the live DB was already at that schema when the port ran, so they're never executed again.
  - **Still true, now for `postgres-js` instead of `pg`**: Supabase's pooler presents its own CA chain (`Supabase Root 2021 CA`) not in Node's bundled trust store, so cert verification needs the CA passed explicitly via `DATABASE_CA_CERT` (PEM content from the Supabase dashboard's Database Settings → SSL Configuration). **Do not put `sslmode=require` (or any `sslmode`) in `DATABASE_URL`**, and never fall back to disabling cert verification to dodge a connection error — fix the actual `ssl` config instead.
  - **No framework DI** — plain modules and exported functions throughout, on purpose (Hono is a router, not an IoC container; rebuilding Nest-style DI on top of it would be pure ceremony). Layering: `src/routes/*.ts` (Hono route definitions, thin — parse input, call a service function, shape the response) → `src/services/*.ts` (business logic, talks to `db` directly) → `src/db/schema.ts` (Drizzle table + relation defs). `src/schemas/*.ts` holds Zod request-validation schemas (one file per domain, mirroring `src/routes/`). Cross-domain reuse is a plain function import (e.g. `services/packages.ts` imports `findOneService` from `services/catalog-services.ts` to validate a `serviceId` belongs to the business before attaching it) — same "never reach into another domain's raw queries" discipline as before, just without a module system enforcing it.
  - Error handling: every thrown error is one of the typed classes in `src/lib/http-error.ts` (`BadRequestError`/`UnauthorizedError`/`ForbiddenError`/`NotFoundError`/`ConflictError`, each fixing an HTTP status), caught by one `app.onError` handler (`src/middleware/error.ts`) that maps status→code exactly as before — `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `409 CONFLICT`, anything else `INTERNAL_ERROR` — into the same `{ error: { code, message } }` envelope (SRS §12) the frontend already unwraps. The code is derived from the numeric status only, never the error class.
  - Validation: `src/lib/validate.ts`'s `parseBody`/`parseQuery`/`parseUuidParam` wrap Zod's `safeParse`, throwing `BadRequestError(issues[0].message)` on failure — only the first message surfaces, matching the old NestJS behavior. Zod's default object behavior already strips unknown keys without erroring (matches the old `ValidationPipe({ whitelist: true })`) — **never add `.strict()`** to a request schema. Body-int fields use plain `z.number().int()` with **no coercion** (`z.coerce.number()` would silently accept `"5"` as a string and diverge from the old behavior of rejecting it). Boolean query params (`?active`) use the shared `booleanQueryParam` helper in `src/schemas/common.ts`: absent → `undefined` (no filter), present → `true` only if literally `"true"`, anything else (including `"false"`) → `false`.
  - Auth: `src/middleware/auth.ts` verifies the `Authorization: Bearer <jwt>` header with `jsonwebtoken` (HS256, `JWT_SECRET`, expiry enforced, **no per-request DB lookup** — same as before) and sets the decoded `{ sub, businessId, email }` payload via `c.set('user', payload)`; route handlers read it with `c.get('user')`. `src/lib/jwt.ts` holds `signJwt`/`verifyJwt`. There is still no registration endpoint separate from `POST /api/auth/signup` (Supabase Auth owns credentials — see below); `pnpm run seed` (`src/seed.ts`) still exists for local dev bootstrapping. Login still never reveals whether the email exists (FR-001) — same generic `UnauthorizedError` either way.
  - **Auth credentials live in Supabase Auth, not this app's tables** (a prior, separate migration off bcrypt — see git history for that story). `src/services/auth.ts`'s `login()` calls `supabase.auth.signInWithPassword()` first (validates password **and** rejects unconfirmed emails), then looks up the local `users` row purely for `businessId` to sign this app's own JWT — the local row is a profile/scoping record, not a credential store. `signup()` calls `supabase.auth.signUp()` then creates the local `businesses`+`users` rows in one `db.transaction`, with `users.id` set explicitly to the Supabase Auth user's own id (same UUID on both sides, no separate correlation column). **The Supabase client (`src/lib/supabase.ts`) must keep `auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false }`** — without it the client assumes a browser environment and crashed the whole Node process on the previous Vercel deploy; this is a hard-won fix, do not remove it.
  - Services/Packages catalog (`src/services/catalog-services.ts`, `src/services/packages.ts`) — both business-scoped (every query filters by `businessId` from the JWT — never trust a client-supplied business id). Services/packages use **deactivate, not delete** — there is deliberately no `DELETE /api/services/:id`; FR-005/006 only ever describe activate/deactivate, and hard-deleting would conflict with `package_services`/`proposal_items` foreign keys. Package↔service composition uses `POST/DELETE /api/packages/:id/services(/:serviceId)` (SRS §8.4) rather than replacing the whole services array on every `PUT`; `addPackageService` is a Drizzle `onConflictDoUpdate` on the `(package_id, service_id)` unique index, guarded by **both** `findOnePackage(businessId, packageId)` and `findOneService(businessId, serviceId)` — the second guard is what stops attaching another tenant's service, don't drop it. `POST /api/packages` is the one package-returning endpoint that does **not** include `items` in the response (it never re-fetches with relations, unlike every other package route) — a deliberate contract quirk preserved from the original, not a bug.
  - Customers (`src/services/customers.ts`), business-scoped like every other domain. `DELETE /api/customers/:id` is a **real hard delete** (SRS §8.2). `removeCustomer` catches the Postgres FK-violation from `proposals.customer_id` (`ON DELETE NO ACTION`/RESTRICT) via `isPgError(err, '23503')` (`src/db/pg-error.ts` — with `postgres-js` the SQLSTATE lands directly on the thrown error, not nested like TypeORM's `driverError.code`) and rethrows as `ConflictError`. `findAllCustomers` supports `?search=` matching name OR phone via case-insensitive partial match (`ilike` + `or()`), per FR-003.
  - Proposals (`src/services/proposals.ts`) — the most complex domain, ported with most care. Price snapshotting (SRS §14) happens in `resolvePackageSnapshot`/`resolveItemSnapshot`, which look up the *current* catalog row and copy name/description/price onto the `proposal_packages`/`proposal_items` row — proposal totals never re-read `package.price`/`service.price` live. `proposal_items` also snapshots `priceType: 'per_day' | 'flat'` — the request may specify which rate to use per line item, or omit it and let `resolveItemSnapshot` infer it (prefers `per_day` if the service has one, else `flat`). Proposal numbers (`WP-{year}-{4-digit sequence}`) are generated by counting existing proposals for that business+year — **not concurrency-safe** (ponytail comment preserved in the code; add a DB sequence/advisory lock if concurrent proposal creation becomes real, don't silently "fix" this without being asked). `PUT /api/proposals/:id` only succeeds while `status === DRAFT` (`ConflictError` otherwise) — packages/items are only replaced when the request actually includes a `packages`/`items` array (omit either to leave that side untouched); when replacing, an item/package **already on the draft may stay even if since deactivated in the catalog — only newly-added ones must be active**, a subtle re-activation rule worth re-reading the code for before touching this path. `createProposal` wraps the proposal insert + child-row inserts in one explicit `db.transaction` (Drizzle has no cascade-on-insert the way TypeORM's `cascade: true` did) so a failure partway through can't leave an orphaned proposal. `findAllProposals`'s `?search=` (matches `customer.name`) can't be expressed in Drizzle's relational-query `where`, so it runs a join-based id lookup first, then a relational re-fetch preserving order — don't try to collapse this into a single relational query.
  - Pricing engine (`src/pricing.ts`) — a deliberately isolated, dependency-free pure function (`calculatePricing`), unit-tested in `src/pricing.spec.ts` with plain vitest, no framework scaffolding of any kind. Implements SRS §17's formula exactly: `subtotal = packageTotal + serviceTotal(excluding optional)` → `discountAmount` (FIXED or PERCENTAGE, clamped to `[0, subtotal]` so total can never go negative, per FR-012) → `taxableAmount = subtotal - discountAmount` → `taxAmount = round(taxableAmount * taxRate / 100)` (tax applies to the **post-discount** amount, confirmed against both the §17 pseudocode and the FR-013 worked example) → `total = taxableAmount + taxAmount`. If you ever suspect the port introduced a pricing bug, `pnpm run test` re-running this file's 7 cases unchanged is the fastest way to confirm the math itself is still correct. `taxRate` lives on **the proposal** (not the business) per SRS §6.1. `createProposal`/`updateProposal`/`calculateProposal` all funnel through a shared `persistPricing()` helper in `services/proposals.ts` so subtotal/discount/tax/total are always recomputed and persisted together, never drifting independently. `POST /api/proposals/:id/calculate` (DRAFT-only like `PUT`) exists so the frontend can adjust discount/tax on an already-saved draft without resending the full packages/items array — `discount: null` in either `calculate` or `PUT` explicitly clears an existing discount (vs. omitting the field entirely, which leaves it untouched — a genuine three-state Zod `.nullish()`, not just optional).
  - PDF generation (`src/pdf.ts`) — a pure `(proposal, business) => Promise<Buffer>` function (pdfkit), no DB access of its own; the caller (`routes/proposals.ts`) fetches `proposal` (with its `customer`/`packages`/`items` relations) and `business` first. `POST /api/proposals/:id/generate-pdf` deliberately returns **200**, not 201 — a leftover quirk from the old Express `@Res()` escape hatch, preserved for frontend compatibility. Hono's `c.body()` needs a `Uint8Array`, not a `Buffer`, for strict TS — wrap with `new Uint8Array(pdfBuffer)`.
- `frontend/` — React + TypeScript via Vite. Package manager **pnpm**. `src/pages/` holds one component per screen; `src/auth/` holds `auth.ts` (localStorage token helpers) and `ProtectedRoute.tsx` (redirects to `/` when unauthenticated); `src/api/client.ts` exports `apiGet`/`apiPost`/`apiPut`/`apiDelete`, all auto-attaching the bearer token and unwrapping the backend's `{ error: { message } }` shape into a thrown `Error`. `src/types/catalog.ts` holds the shared `Service`/`Package`/`PackageItem` interfaces used by the Services/Packages/PackageDetail pages; `src/types/customer.ts` holds `Customer`; `src/types/proposal.ts` holds `Proposal`/`ProposalPackage`/`ProposalItem`. `CreateProposal.tsx` implements SRS §10.2's sections 1–4/6/7 in one screen but **merges §10.2's sections 4 ("Individual services") and 5 ("Optional services") into a single Services section** with an inline `isOptional` checkbox per line — functionally equivalent (still produces `ProposalItem.isOptional`, still visually splits into "Included"/"Optional" groups) but avoids a duplicate add-service flow. Its Pricing section's discount-type/value and tax-rate inputs are pre-save only (submitted with the initial `POST /api/proposals`) — there's no post-save "adjust and recalculate" UI wired to `POST /api/proposals/:id/calculate` yet even though the backend supports it; that's a natural fit for Phase 6's editing screen rather than Phase 5. `PackageServiceSelection.tsx` (a Phase-0-scaffolded route, `/proposals/new/packages`) is unused dead code from before this design was settled — nothing links to it, left alone per the surgical-changes rule. `ProposalPreview.tsx`/`ProposalHistory.tsx` remain stubs; SRS §10.2's dedicated Preview screen is explicitly Phase 6 (FR-014/015), not Phase 4/5.

Beyond Phases 0–5, no further domain feature code exists yet — implement remaining FRs from the SRS into these two projects rather than restructuring them. The phase-by-phase build order lives in the active plan file (ask if you need it re-surfaced).

## Commands

Run from the repo root:

```
pnpm run dev             # start backend (watch) + frontend dev server together, via concurrently
```

All other commands run from inside `backend/` or `frontend/` respectively.

```
pnpm install            # install deps
pnpm run start          # backend: run the Hono app via @hono/node-server (localhost:3333)
pnpm run start:dev      # backend: watch mode (tsx watch)
pnpm run build          # backend: tsc --noEmit typecheck (Vercel bundles src/index.ts itself, no local build artifact); frontend: production build
pnpm run test           # backend: unit tests (vitest) -- currently just src/pricing.spec.ts
pnpm run db:generate    # backend: diff src/db/schema.ts vs the last migration into a new Drizzle migration
pnpm run db:migrate     # backend: apply pending Drizzle migrations (Supabase)
pnpm run seed           # backend: create/re-link the dev business + admin user (SEED_ADMIN_EMAIL/PASSWORD from .env)
pnpm dev                # frontend: Vite dev server (localhost:5173, or next free port)
```

Both `backend/.env` and `frontend/.env` hold real local config (`DATABASE_URL` and `DATABASE_CA_CERT` for Supabase, `JWT_SECRET`, `SEED_ADMIN_EMAIL`/`PASSWORD`, `VITE_API_URL`) — copy from the corresponding `.env.example` when setting up a new machine; both are gitignored. Backend runs on **port 3333**, not 3000 — an unrelated, unidentified long-running process occupies 3000 on this dev machine (unkillable without elevated privileges); investigate that separately if you need port 3000 back.

## Product shape (for orientation)

**Domain:** internal sales tool for a wedding photography business to build customer proposals/quotations and export them as PDF.

**Core entity graph:**
```
Business → Users, Customers, Services, Packages
Customer → Proposals
Proposal → ProposalPackages, ProposalItems
Package ↔ Service (many-to-many via PackageService)
```

**Non-negotiable business rules baked into the data model (SRS §14, FR-007/008):**
- A proposal can hold *multiple* packages plus individual services plus optional add-ons simultaneously — this drives the schema (`ProposalPackage` and `ProposalItem` as separate child tables, not a single line-items table).
- **Price snapshotting**: when a package/service is added to a proposal, its name/description/price must be copied onto the `ProposalPackage`/`ProposalItem` row. Later catalog price changes must never alter existing proposals. Any pricing code that reads `package.price`/`service.price` live at proposal-render time instead of the stored snapshot is a bug.
- **Backend is the pricing authority** (FR-011, §13 Security): the frontend must never be trusted to compute or submit a final total. Reject/ignore any client-supplied total; recompute server-side from package/service IDs and quantities.
- Optional services (`is_optional`) are excluded from the totals by default and only added in when explicitly included.
- Multi-tenancy: all data is scoped by `business_id`; one business must never see another's data (§13 Authorization).

**Stack (decided):** Hono + TypeScript backend (Vercel Functions, previously NestJS — ported for cold-start/deploy reasons, see `backend/` notes above), React (not Next.js) + TypeScript frontend, PostgreSQL via Drizzle ORM (previously TypeORM), server-side PDF generation. This overrides the SRS §16 suggestion of Next.js/Express — use React/Hono specifically.

**Code comments:** keep minimal. Do not write comments unless the WHY is non-obvious (a hidden constraint, workaround, or non-obvious invariant) — never comment on WHAT the code does.

**Design principles:** apply SOLID, and favor high cohesion / low coupling, in both backend and frontend code.
- Single Responsibility: keep Hono route handlers thin (parse input, call a service function, shape the response) — business logic lives in `src/services/*.ts`, persistence in `src/db/schema.ts`. Don't let a route handler or a React component grow multiple reasons to change.
- Open/Closed & Liskov: prefer extending via new functions/strategies (e.g. new discount types, new PDF templates) over branching on type flags inside existing logic.
- Interface Segregation & Dependency Inversion: without a DI container, this mostly means keeping each `src/services/*.ts` file's exported functions narrow and composable — a domain that needs another domain's logic imports its specific function (e.g. `findOneService`), never its raw table/query. The one place this project deliberately used to lean on an interface+injection-token (PDF generation) collapsed to a plain function on the Hono port, since it only ever had one implementation — don't reintroduce that indirection speculatively; add it back only if a second PDF backend or similar genuinely shows up.
- Cohesion/coupling in practice: each domain (`business`, `catalog-services`, `packages`, `customers`, `proposals`, `auth`) should own its own `src/services/*.ts` + `src/routes/*.ts` + `src/schemas/*.ts` file and expose only what other domains need; cross-domain reach-ins (e.g. proposals importing packages' Drizzle queries directly instead of its service functions) are a smell. On the frontend, keep components/hooks focused on one concern (data-fetching vs. presentation vs. form state) rather than monolithic page components.

**Architecture guidance from the spec** (SRS §15 Maintainability): keep the pricing engine as an isolated, unit-tested module separate from route/controller code (pseudocode in SRS §17), and keep PDF generation decoupled from proposal calculation.

## Explicitly out of scope for the MVP

Do not add unless asked: online payments, customer login/portal, WhatsApp/email automation, e-signatures, booking/contract management, full CRM, AI chatbot, analytics, multi-language/multi-currency, complex tax/discount rules. AI-based requirement extraction is a documented future phase (SRS §24) — not part of the MVP build.
